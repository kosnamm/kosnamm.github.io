Git Workflow

Git是一个免费开源的分布式版本控制系统，旨在快速高效地处理从大到小的各种项目。在现如今的软件开发领域，无论我们从事何种形式的开发，Git基本上都是版本管理的必然选择，Git将会伴随项目代码的整个生命周期。在这篇文章当中，我们不会详细解释每一个Git命令，而是基于Github Flow工作流程来介绍如何在多人合作的代码仓库当中，优雅地完成一次commit。 工欲善其事，必先利其器。正式开始之前，先看一下如何下载Git。 MacOS MacOS下推荐使用brew下载Git： brew install git Windows和Linux系统下Git官网也提供了专用的下载方式。 当完成Git的下载安装后，可以使用git --version命令在终端中检查是否成功安装，正常情况下会输出所安装Git的版本号。 git --version First Commit 在开始多人协作之前，我们先从一次最基础的本地提交开始。Git管理代码并不是直接把文件塞进版本历史，而是会经历三个区域。 raw workspace raw workspace就是我们平时直接编辑文件的工作区。你在IDE或编辑器里新增、删除、修改的内容，最开始都只存在于这个区域。此时Git可以感知到文件发生了变化，但这些变化还没有被纳入下一次提交。 git workspace git workspace通常也被称为暂存区，也就是stage。当我们执行git add时，Git会把指定文件的当前状态放入暂存区。暂存区的意义是让我们可以精确控制下一次commit到底包含哪些改动。 commit 当我们执行git commit时，Git会把暂存区中的内容保存成一个快照，并生成一个唯一的commit id。commit id可以理解为这次代码状态的身份证，后续的代码回退、版本比较、问题定位都会依赖它。 一次最小的本地提交流程如下： # 查看当前仓库中发生了哪些变化 git status # 将所有变更加入暂存区 git add . # 创建一次提交 git commit -m "init project" 这里的git add .表示把当前目录下的全部变更都加入暂存区。它很方便，但在真实项目中也要谨慎使用：如果你临时修改了配置文件、日志文件或实验代码，它们也可能被一起加入commit。更稳妥的做法是先通过git status确认变更，再使用更明确的路径。 git add src/main.go git add README.md 如果你想检查某个文件具体改了什么，可以使用： git diff 如果文件已经被加入暂存区，想查看暂存区中的差异，可以使用： git diff --staged git commit -m后面的内容是commit message。它不是随便写给机器看的字符串，而是写给未来的自己和协作者看的上下文。一个好的commit message应该能说明这次提交完成了什么事情，例如： ...

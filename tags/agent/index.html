Agent-Assisted Workflow

目前，大多数 Agent 框架都围绕 ReAct、Reflection 或 Planning 等模式构建 Runtime。Agent 通过观察上下文、选择 Skill、调用 Tool，逐步完成目标。它的执行路径并非预先写死，而是由模型根据当前状态动态决定。 这种模式非常适合开放式任务：Agent 可以根据局部反馈不断调整下一步动作，在庞大的解空间中探索一条可行路径。它的局限也来自同一套机制——局部最优的选择未必能保证全局目标稳定达成。一次工具调用失败、上下文丢失、外部服务超时，或者中间结果格式变化，都可能让后续决策逐渐偏离原本的目标。单纯增加重试次数通常只能缓解网络抖动，无法修复已经不确定的执行状态。 另一种思路是使用 Workflow，把任务拆成一组由代码定义的步骤。Workflow 能够提供稳定的结构、输入输出契约和执行边界；但如果正常路径、异常分支和恢复逻辑都被硬编码，它又很容易膨胀成难以维护的固定脚本。一旦外部环境或中间状态超出预设分支，流程仍然只能失败退出或等待人工介入。 本文讨论一种介于两者之间的设计：Workflow 仍然由代码定义，Agent 不替代 Workflow，而是在执行发生偏差时介入，负责诊断问题并提出局部恢复方案。 两种模式最关键的区别，在于 Action 的所有权。在传统 ReAct 模式中，Agent 决定调用什么 Tool、如何调用以及下一步做什么；在 Agent-Assisted Workflow 中，正常步骤和副作用的执行权属于 Workflow，Agent 只在边界内处理异常与不确定性。这样既保留了自动化流程的稳定性，也为预设规则覆盖不到的情况提供了适应能力。 The Core Idea 传统 Workflow 主要回答： What should happen next?

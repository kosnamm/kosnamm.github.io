Agent-Assisted Workflow

September 3, 2026 · 2 min · 402 words · Matthew G | Suggest Changes

目前，大多数 Agent 框架都围绕 ReAct、Reflection 或 Planning 等模式构建 Runtime。Agent 通过观察上下文、选择 Skill、调用 Tool，逐步完成目标。它的执行路径并非预先写死，而是由模型根据当前状态动态决定。

这种模式非常适合开放式任务：Agent 可以根据局部反馈不断调整下一步动作，在庞大的解空间中探索一条可行路径。它的局限也来自同一套机制——局部最优的选择未必能保证全局目标稳定达成。一次工具调用失败、上下文丢失、外部服务超时，或者中间结果格式变化，都可能让后续决策逐渐偏离原本的目标。单纯增加重试次数通常只能缓解网络抖动，无法修复已经不确定的执行状态。

另一种思路是使用 Workflow，把任务拆成一组由代码定义的步骤。Workflow 能够提供稳定的结构、输入输出契约和执行边界；但如果正常路径、异常分支和恢复逻辑都被硬编码，它又很容易膨胀成难以维护的固定脚本。一旦外部环境或中间状态超出预设分支，流程仍然只能失败退出或等待人工介入。

本文讨论一种介于两者之间的设计：Workflow 仍然由代码定义，Agent 不替代 Workflow，而是在执行发生偏差时介入，负责诊断问题并提出局部恢复方案。

两种模式最关键的区别，在于 Action 的所有权。在传统 ReAct 模式中，Agent 决定调用什么 Tool、如何调用以及下一步做什么；在 Agent-Assisted Workflow 中，正常步骤和副作用的执行权属于 Workflow，Agent 只在边界内处理异常与不确定性。这样既保留了自动化流程的稳定性，也为预设规则覆盖不到的情况提供了适应能力。

The Core Idea#

传统 Workflow 主要回答：

What should happen next?

Agent-Assisted Workflow 更关注：

What must be true before this workflow can continue?

这张图展示了三者的职责边界：Workflow 驱动从输入、步骤执行、状态校验到结果提交的主路径；Agent 只在执行或校验出现偏差时介入，诊断问题并提出恢复方案；Runtime 则提供 checkpoint、事件日志、策略校验和幂等保障。Agent 的建议必须经过 Runtime 校验，最终仍由 Workflow 执行合法动作。

Workflow 负责定义结构和约束：

  • 步骤和阶段
  • 输入输出契约
  • 前置条件和后置条件
  • 允许的 Tool 和 Skill
  • 可恢复的错误类型
  • 需要人工确认的高风险操作

Agent 负责处理执行过程中的不确定性：

  • 判断失败原因
  • 区分临时错误和状态错误
  • 选择重试、替代 Tool 或补偿动作
  • 从 checkpoint 恢复上下文
  • 修复不完整的中间结果
  • 生成局部恢复计划

因此，Workflow 依然是系统的控制边界，Agent 则是 Workflow 中具备自适应能力的恢复决策者。它可以提出“如何回到可继续状态”，但不能绕过流程直接制造新的状态。

A Code-Defined Workflow#

一个简单的 Workflow 可以由代码显式定义：

workflow = Workflow(
    steps=[
        FetchData(),
        TransformData(),
        ValidateResult(),
        PublishReport(),
    ]
)

每个步骤不只实现一个 execute 方法，还应该声明自己的执行契约：

Step(
    name="publish_report",
    execute=publish_report,
    precondition=report_is_valid,
    postcondition=report_is_published,
    recovery_policy="agent_assisted",
)

这种定义方式保留了 Workflow 的可读性和可测试性。开发者可以清楚地看到任务由哪些阶段组成，也可以针对每个步骤编写单元测试，而不需要把所有逻辑交给模型。

Where the Agent Intervenes#

Agent 不应该参与每一次正常的步骤转移。正常路径应当尽可能确定：满足前置条件就执行步骤，满足后置条件就进入下一步。

Agent 主要在以下生命周期事件中介入：

on_step_failure
on_step_timeout
on_precondition_failed
on_postcondition_failed
on_invalid_output
on_resume

例如，上传报告时发生网络超时，系统不能直接重新执行上传：请求可能已经在服务端成功，只是客户端没有收到响应。恢复 Agent 应该先分析当前状态：

1. Check whether the report has already been uploaded.
2. Reuse the original operation_id and idempotency key.
3. Retry only when the upload is confirmed incomplete.
4. Pause for human approval when the final state is unknown.

Agent 的目标不是“想办法继续运行”，而是在 Workflow 约束之内，把当前状态恢复到可以继续执行的状态。

Resume After Interruption#

要实现可靠的恢复，Runtime 需要在步骤边界保存 checkpoint，并记录工具调用事件：

WorkflowRun
  - run_id
  - workflow_version
  - current_step
  - execution_state
  - checkpoints
  - tool_call_records
  - pending_side_effects

进程重启后，Runtime 不应该从头执行 Workflow，而是按照下面的流程恢复：

Load checkpoint
      |
Replay execution events
      |
Find the last incomplete step
      |
Agent diagnoses the interruption
      |
Validate the recovery plan
      |
Resume or pause the workflow

这里需要接受一个现实：外部系统通常无法保证真正的 exactly-once execution。更实际的实现是使用 at-least-once execution，再结合幂等键、操作记录和结果查询，避免恢复时重复产生副作用。

Runtime Integration#

这层能力可以通过 Supervisor 介入现有的 ReAct 或 Reflection Runtime，而不需要重写 Agent：

Workflow Supervisor
  - checkpoint store
  - event log
  - policy validator
  - recovery planner
          |
          v
Agent Runtime
  - ReAct loop
  - Reflection
  - Tool selection
          |
          v
Skills and Tools

一个最小的接口可以这样设计：

class WorkflowSupervisor:
    async def run(self, workflow, input_data):
        context = await self.store.create(workflow, input_data)
        return await self.drive(context)

    async def resume(self, run_id):
        context = await self.store.load(run_id)
        diagnosis = await self.recovery_agent.diagnose(context)
        plan = await self.recovery_agent.plan(diagnosis)
        await self.policy.validate(plan, context)
        return await self.drive(context, plan)

drive 方法负责执行 Workflow 的确定性部分；recovery_agent 只负责处理偏离预期的局部状态。它可以从当前步骤允许的动作中提出恢复计划，但不能直接执行任意 Tool。所有恢复动作都必须经过 Workflow 的策略校验，再由 Runtime 驱动执行。

Controlled Autonomy#

Agent 参与恢复并不意味着它可以随意跳过步骤。为了防止自适应能力变成不可控行为，Workflow 至少需要限制三个方面：

  1. Allowed actions：Agent 只能调用当前步骤声明过的 Tool 和 Skill。
  2. State transitions：Agent 不能直接修改 Workflow 状态，必须通过合法的 transition 更新。
  3. Side effects：发送消息、修改数据或发布资源等副作用必须具备幂等性，必要时需要人工审批。

恢复计划可以先以结构化格式输出，再由 Runtime 校验：

{
  "action": "query_upload_status",
  "reason": "upload result is unknown",
  "operation_id": "op_123",
  "next": "retry_upload_if_missing"
}

模型负责提出计划，Runtime 负责判断计划是否合法。这个边界很重要：Agent 可以提高 Workflow 的弹性，但不能成为绕过 Workflow 约束的后门。

Conclusion#

固定 Workflow 的问题不在于代码定义流程本身，而在于它通常把异常路径也写成了固定脚本。现实环境中的失败具有不确定性，恢复过程需要理解上下文、判断状态并选择合适的动作。

Agent-Assisted Workflow 保留了代码定义 Workflow 的结构性，同时借助 Agent 的推理能力处理异常路径：

Code defines the workflow.
Agent diagnoses deviations.
Runtime validates recovery.
Checkpoint makes execution resumable.

这使得 Agent 不再只是一次性的 ReAct Loop，也不需要把整个任务交给一个不可预测的自主循环。Workflow 提供边界，Agent 提供适应性，Runtime 则负责把两者连接成一个可以长期运行和恢复的执行系统。

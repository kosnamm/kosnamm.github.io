Git Workflow

March 24, 2026 · 3 min · 449 words · Matthew G | Suggest Changes

Git是一个免费开源的分布式版本控制系统，旨在快速高效地处理从大到小的各种项目。在现如今的软件开发领域，无论我们从事何种形式的开发，Git基本上都是版本管理的必然选择，Git将会伴随项目代码的整个生命周期。在这篇文章当中，我们不会详细解释每一个Git命令，而是基于Github Flow工作流程来介绍如何在多人合作的代码仓库当中，优雅地完成一次commit。

工欲善其事，必先利其器。正式开始之前，先看一下如何下载Git。

MacOS

MacOS下推荐使用brew下载Git：

brew install git

Windows和Linux系统下Git官网也提供了专用的下载方式。

当完成Git的下载安装后，可以使用git --version命令在终端中检查是否成功安装，正常情况下会输出所安装Git的版本号。

git --version

First Commit#

在开始多人协作之前，我们先从一次最基础的本地提交开始。Git管理代码并不是直接把文件塞进版本历史，而是会经历三个区域。

raw workspace

raw workspace就是我们平时直接编辑文件的工作区。你在IDE或编辑器里新增、删除、修改的内容，最开始都只存在于这个区域。此时Git可以感知到文件发生了变化，但这些变化还没有被纳入下一次提交。

git workspace

git workspace通常也被称为暂存区，也就是stage。当我们执行git add时，Git会把指定文件的当前状态放入暂存区。暂存区的意义是让我们可以精确控制下一次commit到底包含哪些改动。

commit

当我们执行git commit时，Git会把暂存区中的内容保存成一个快照，并生成一个唯一的commit id。commit id可以理解为这次代码状态的身份证，后续的代码回退、版本比较、问题定位都会依赖它。

一次最小的本地提交流程如下：

# 查看当前仓库中发生了哪些变化
git status

# 将所有变更加入暂存区
git add .

# 创建一次提交
git commit -m "init project"

这里的git add .表示把当前目录下的全部变更都加入暂存区。它很方便，但在真实项目中也要谨慎使用：如果你临时修改了配置文件、日志文件或实验代码，它们也可能被一起加入commit。更稳妥的做法是先通过git status确认变更，再使用更明确的路径。

git add src/main.go
git add README.md

如果你想检查某个文件具体改了什么，可以使用：

git diff

如果文件已经被加入暂存区，想查看暂存区中的差异，可以使用：

git diff --staged

git commit -m后面的内容是commit message。它不是随便写给机器看的字符串，而是写给未来的自己和协作者看的上下文。一个好的commit message应该能说明这次提交完成了什么事情，例如：

git commit -m "add user login api"
git commit -m "fix order amount rounding"
git commit -m "refactor payment callback parser"

不要使用过于模糊的描述，例如：

git commit -m "update"
git commit -m "fix bug"
git commit -m "change code"

这些信息在当下看起来也许无所谓，但当团队需要排查线上问题、回滚代码或理解历史变更时，模糊的commit message会显著增加沟通成本。

Github Flow#

当代码只属于一个人时，直接在main分支上提交也许还能接受。但在多人协作的项目中，大家同时修改同一个主分支会带来很多问题：代码互相覆盖、未完成的功能被提前发布、线上问题难以定位、review过程缺少明确边界。

Github Flow是一种轻量但清晰的协作流程，它的核心思想是：

  1. main分支始终保持稳定。
  2. 所有新功能、bug fix、重构都从main切出一个新的分支。
  3. 开发完成后推送到远程仓库，并创建Pull Request。
  4. 经过代码审查和测试后，再合并回main。

这个流程不会引入复杂的长期分支，也不会要求每个项目都有固定的发布分支。对于大多数Web服务、业务系统、脚本工具和学习项目来说，它已经足够好。

1. 同步主分支#

开始开发前，先确保本地main分支是最新的。

git checkout main
git pull origin main

git checkout main表示切换到本地main分支，git pull origin main表示从远程仓库的main分支拉取最新代码并合并到本地。

如果你的仓库主分支叫master，把命令中的main替换为master即可。

2. 创建开发分支#

不要直接在main上开发，而是从最新的main切出一个语义清晰的分支。

git checkout -c feature/user-login

分支名最好能表达工作内容。常见前缀包括：

  • feature/：新功能，例如feature/user-login
  • fix/：bug修复，例如fix/order-total
  • refactor/：重构，例如refactor/payment-service
  • docs/：文档修改，例如docs/git-workflow

分支名不是给Git看的，而是给协作者看的。一个清晰的分支名可以让别人不用点进代码，也能大致知道你在做什么。

3. 修改代码并提交#

在开发分支上完成代码修改后，先查看状态：

git status

再检查差异：

git diff

确认无误后，把需要提交的文件加入暂存区：

git add src/login.go
git add tests/login_test.go

然后创建commit：

git commit -m "add user login endpoint"

一次commit最好只表达一个相对完整的意图。如果你同时修了登录接口、格式化了无关文件、又改了部署脚本，这些改动最好拆成不同的commit。这样review时更容易理解，出问题时也更容易回滚。

4. 推送分支到远程仓库#

本地commit只存在于你的电脑上。要让Github上的协作者看到这次改动，需要把分支推送到远程仓库。

git push -u origin feature/user-login

第一次推送新分支时使用-u，Git会记录本地分支和远程分支的关联关系。之后在这个分支上继续推送，只需要执行：

git push

5. 创建Pull Request#

分支推送到Github后，就可以创建Pull Request。Pull Request通常简称PR，它不是单纯的合并按钮，而是一次围绕代码变更展开的协作入口。

一个好的PR应该说明：

  • 这次改动解决了什么问题
  • 主要改了哪些内容
  • 是否有需要特别关注的地方
  • 如何验证这次改动

例如：

## What

Add user login endpoint and token generation logic.

## Why

Users need to sign in before accessing private resources.

## Test

- Run unit tests for login service
- Verify login success and invalid password cases locally

PR的核心价值在于让代码进入主分支之前，先被讨论、审查和验证。对于多人协作项目来说，这一步比单纯提交代码更重要。

6. 根据Review修改代码#

PR创建后，协作者可能会留下review comment。修改方式仍然是在同一个开发分支上继续提交。

# 修改代码后
git status
git add src/login.go
git commit -m "handle invalid login input"
git push

推送后，PR会自动更新。不要因为review comment就关闭原来的PR再开一个新的PR，除非分支方向已经完全变化。保持同一个PR可以保留完整的讨论上下文。

7. 合并并清理分支#

当PR通过review和测试后，就可以合并到main。合并通常在Github网页上完成。合并后，本地也需要同步主分支：

git checkout main
git pull origin main

如果开发分支已经不再需要，可以删除本地分支：

git branch -d feature/user-login

远程分支通常可以在Github合并PR后通过页面上的按钮删除，也可以使用命令：

git push origin --delete feature/user-login

至此，一个完整的Github Flow就完成了。

Beyond First Commit#

理解了基础流程后，我们还需要处理几个真实协作中经常遇到的问题。这些问题不会改变Github Flow的主干流程，但会影响你提交代码的质量。

撤销暂存区#

如果你执行了git add .，但发现有些文件不应该进入本次commit，可以把它们从暂存区移除：

git restore --staged config.local.toml

这条命令不会删除你的文件修改，只是让它退出暂存区，回到raw workspace。

丢弃本地修改#

如果你确认某个文件的本地修改完全不要了，可以使用：

git restore src/login.go

这会把文件恢复到最近一次commit的状态。这个操作会丢弃工作区修改，执行前一定要确认这些改动不再需要。

修改最后一次commit#

如果刚提交完就发现漏了一个文件，或者commit message写错了，可以使用--amend修改最后一次commit。

git add README.md
git commit --amend

如果只想修改commit message：

git commit --amend -m "add user login endpoint"

需要注意的是，--amend会生成一个新的commit id。如果这个commit已经推送到远程并被别人基于它继续开发，修改历史会带来额外成本。因此它更适合用于尚未共享出去的本地commit。

解决冲突#

多人同时修改同一个文件时，合并代码可能会产生conflict。Git会在冲突文件中标记不同版本的内容：

<<<<<<< HEAD
local change
=======
remote change
>>>>>>> main

解决冲突不是简单地删除标记，而是要理解两边改动的意图，保留最终正确的代码。处理完成后，再执行：

git add conflicted-file.go
git commit

如果冲突发生在git pull过程中，Git通常会继续完成一次merge commit。如果冲突发生在rebase过程中，则需要使用：

git rebase --continue

保持分支更新#

如果你的开发分支存在时间较长，main可能已经有了新的提交。为了减少最终合并时的冲突，可以定期把main的最新代码同步到当前分支。

比较直观的方式是merge：

git checkout feature/user-login
git fetch origin
git merge origin/main

merge会保留一条明确的合并记录，历史更真实，但提交图可能会更复杂。

另一种方式是rebase：

git checkout feature/user-login
git fetch origin
git rebase origin/main

rebase会把你的提交移动到最新main之后，让提交历史更线性。但它会改写当前分支的commit id，因此不要随意rebase别人也在使用的公共分支。

简单来说：

  • 个人开发分支可以使用rebase保持历史整洁。
  • 多人共享分支优先使用merge，避免改写别人依赖的历史。

A Complete Example#

下面是一套从开始开发到提交PR的完整命令。

# 1. 回到主分支并同步最新代码
git checkout main
git pull origin main

# 2. 创建开发分支
git checkout -b feature/user-login

# 3. 修改代码后查看变化
git status
git diff

# 4. 暂存并提交
git add src/login.go tests/login_test.go
git commit -m "add user login endpoint"

# 5. 推送远程分支
git push -u origin feature/user-login

接下来在Github上创建Pull Request，等待review和CI检查。合并后再同步本地main：

git checkout main
git pull origin main
git branch -d feature/user-login

Commit Checklist#

在提交代码前，可以快速检查下面几件事：

  • git status中没有不该提交的文件。
  • git diff里的改动和本次任务相关。
  • commit message能清楚说明这次提交做了什么。
  • 本地测试或必要的验证已经完成。
  • 分支名和PR描述能让协作者理解这次改动。

Git本身只是一套版本管理工具，真正决定协作质量的是我们如何使用它。一个清晰的分支、一组干净的commit、一次有上下文的PR，会让代码审查、问题回溯和长期维护都变得轻松很多。
